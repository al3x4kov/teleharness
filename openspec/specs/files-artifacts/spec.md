# Files-Artifacts Specification

## Purpose

Вложения и артефакты: загрузка файлов любых форматов со щедрыми лимитами в .zai-uploads, чипы-артефакты только из write/edit в папке сессии, превью и скачивание через FileViewer в рамках разрешённых корней.

## Requirements

### Requirement: Загрузка любых форматов

Система SHALL принимать вложения без белого списка форматов: картинки идут в сообщение inline, остальные файлы загружаются стримом в .zai-uploads внутри директории сессии и передаются агенту текстовой ссылкой, в пузыре — чип файла. (трекер: FEAT-05.1)

#### Scenario: Таблица с телефона

- **WHEN** пользователь прикрепляет xlsx (в том числе ~9 МБ) и отправляет сообщение
- **THEN** файл загружается, в чате виден чип вложения, агент получает файл и может его читать

### Requirement: Лимиты загрузки

Система SHALL ограничивать вложения: не более 100 МБ на файл, не более 20 файлов за раз и не более 500 МБ суммарно на сообщение; превышение отклоняется с понятным сообщением. (трекер: FEAT-05.2)

#### Scenario: Превышение лимита

- **WHEN** прикрепляется 21-й файл, файл больше 100 МБ или сумма больше 500 МБ
- **THEN** загрузка отклоняется с понятным сообщением об ограничении

### Requirement: Чипы только из write/edit сессии

Система SHALL показывать чипы-артефакты только для файлов, созданных или изменённых инструментами write/edit в папке сессии, и для собственных вложений из .zai-uploads: упомянутые в тексте пути не становятся чипами, незапрошенные файлы сервера и временные файлы агента (системные temp-каталоги) не показываются. (трекер: FEAT-05.6, BUG-05.8 (BUG-012))

#### Scenario: Сгенерированный файл

- **WHEN** агент завершает write/edit файла в папке сессии
- **THEN** в сообщении появляется чип-артефакт с превью и скачиванием

#### Scenario: Незапрошенные файлы скрыты

- **WHEN** ответ упоминает пути исходников портала, vault или системных файлов
- **THEN** такие пути не превращаются в чипы и не предлагаются к скачиванию

#### Scenario: Временный скрипт агента

- **WHEN** агент пишет вспомогательный скрипт в системный Temp-каталог
- **THEN** чип для этого файла не появляется

### Requirement: Превью и скачивание

Система SHALL открывать чип в FileViewer с превью по типу (картинка, pdf, html в песочнице, md, текст, csv, видео, аудио) и скачиванием; для office/zip — карточка скачивания; скачивание байт-в-байт совпадает с оригиналом, доступ к файлам — только в рамках разрешённых корней (ZAI_FILE_ROOTS; выход за корни — 403). FileViewer рендерится порталом в body: на iOS превью скроллится, закрывается и скачивает файл. (трекер: FEAT-05.3, BUG-05.4, BUG-05.5)

#### Scenario: Превью вне директории сессии

- **WHEN** чип ведёт на файл в разрешённом корне вне папки сессии
- **THEN** превью открывается, а попытка выйти за разрешённые корни завершается 403

#### Scenario: Скачивание

- **WHEN** пользователь нажимает скачивание
- **THEN** полученный файл байт-в-байт совпадает с оригиналом

#### Scenario: Превью на iPhone

- **WHEN** пользователь открывает длинный документ в FileViewer на iPhone
- **THEN** содержимое скроллится, кнопка закрытия и скачивание работают

### Requirement: Карточки файлов в ответе

Система SHALL показывать каждый файл-результат ответа ассистента карточкой во всю ширину: плашка с иконкой типа (у картинки — миниатюра), имя без расширения и подпись «Тип · РАСШИРЕНИЕ». Несколько файлов — стопкой перед итоговым текстом сообщения; тап открывает FileViewer. (трекер: FEAT-05.17)

#### Scenario: Один документ

- **GIVEN** агент записал файл `opencode-obsidian-setup.md` в папке сессии
- **WHEN** ответ отрисован
- **THEN** под шагами и перед текстом ответа видна карточка «opencode-obsidian-setup» с подписью «Документ · MD», а тап по ней открывает превью

#### Scenario: Несколько файлов разных типов

- **GIVEN** агент записал `crpv-schema.html`, `crpv-schema.drawio`, `crpv-schema.md` и `crpv-model-preview.png`
- **WHEN** ответ отрисован
- **THEN** видны четыре карточки стопкой с подписями «Код · HTML», «Файл · DRAWIO», «Документ · MD», «Изображение · PNG», у картинки в плашке её миниатюра

#### Scenario: Угаданная картинка не существует

- **GIVEN** в тексте ответа упомянута относительная картинка, которой нет на диске
- **WHEN** миниатюра не загрузилась
- **THEN** карточка этой картинки не показывается

### Requirement: Картинка для модели без image input

Если модель opencode-чата admin по каталогу не принимает изображения, сервер SHALL сохранять приложенную картинку в `.zai-uploads` папки чата и передавать вместо неё путь с подсказкой для vision-субагента; vision-модели и движок Claude получают картинку как раньше. (трекер: FEAT-03.12, BUG-140)

#### Scenario: Картинка дефолтному агенту

- **GIVEN** дефолтный агент на текстовой модели
- **WHEN** пользователь прикладывает картинку и просит её описать
- **THEN** агент описывает содержимое картинки по существу

### Requirement: Картинка тенанта на модели без image input

Если модель opencode-чата тенанта (у него нет vision-субагента) по каталогу не принимает изображения, сервер SHALL отправлять этот ход модели со зрением того же провайдера из каталога тенанта (по умолчанию `glm-5.3-flash`, `ZAI_TENANT_VISION_MODEL`) с картинкой напрямую, не меняя привязку чата; нет такой модели — как у admin. (трекер: BUG-04.12)

#### Scenario: Тенант на текстовой GLM

- **GIVEN** тенант, чат привязан к `zai-coding-plan/glm-5.3` (без image input), агент Sandbox
- **WHEN** тенант прикладывает картинку и просит её описать
- **THEN** ход уходит модели `glm-5.3-flash`, ответ описывает содержимое картинки, привязка чата остаётся `glm-5.3`, следующий ход без картинки идёт на `glm-5.3`

### Requirement: Проверка существования угаданных картинок

Клиент SHALL вставлять `<img>` для угаданного из текста пути только после подтверждения существования файла через `GET /zai/api/file/exists`. (трекер: BUG-090)

#### Scenario: Удалённая картинка

- **WHEN** в ответе упомянут путь к уже удалённой картинке
- **THEN** превью не показывается и в консоли нет 404

### Requirement: Миниатюры картинок-артефактов

Система SHALL показывать картинку, созданную агентом, миниатюрой прямо в сообщении (а не чипом-документом), с открытием в FileViewer; результат-вложение отображается в чате, а не адресом на сервере. (трекер: BUG-05.9, FEAT-05.7)

#### Scenario: Агент сгенерировал PNG

- **WHEN** агент записывает картинку в папку сессии
- **THEN** в сообщении видна её миниатюра, нажатие открывает превью

### Requirement: Превью таблиц и документов

Система SHALL показывать в FileViewer превью xlsx (таблица листа) и docx (текст документа) вместо одной карточки скачивания. (трекер: FEAT-05.10)

#### Scenario: Открытие xlsx

- **WHEN** пользователь открывает чип xlsx-файла
- **THEN** FileViewer показывает содержимое листа и кнопку скачивания

### Requirement: Карточки файлов хода из папки чата

Система SHALL показывать карточками файлов ответа файлы, созданные или изменённые в папке чата за время хода любым способом (write/edit, скрипт, команда), в обоих движках, если ход называет файл — в тексте ответа, во входе, выводе или заголовке инструмента. Файл, который ход не называл (записан другим чатом или процессом в общую папку), карточкой не становится. (трекер: BUG-092 / BUG-05.18, BUG-05.19 (BUG-094))

#### Scenario: Файлы, созданные скриптом

- **GIVEN** Claude-ход создал скриптом семь файлов md, csv, html, docx, png, svg, jpeg в подпапке папки чата и перечислил их в ответе
- **WHEN** ход закрылся
- **THEN** в ответе семь карточек с подписями по типам, у картинок миниатюры по настоящему пути, а в консоли нет 404

#### Scenario: Чужой файл в общей папке

- **GIVEN** чат в HOME, ход ответил «ок»; во время хода другой процесс создал probe-leak.txt в HOME
- **WHEN** ход закрылся
- **THEN** карточки probe-leak.txt под ответом нет

### Requirement: Серверный список файлов хода

Система SHALL получать список файлов хода от сервера по окнам закрытых ходов, только в пределах прав пользователя на папку и без скрытых, служебных и временных файлов. Имя файла, угаданное по тексту ответа, показывается карточкой только если сервер подтвердил файл. (трекер: BUG-092 / BUG-05.18)

#### Scenario: Чужая папка

- **GIVEN** тенант запрашивает список файлов хода для папки вне своей области
- **WHEN** запрос приходит на сервер
- **THEN** сервер отвечает 403 и ничего не перечисляет

### Requirement: Пути Git Bash в командах хода

Система SHALL понимать пути Git Bash вида /d/… в командах хода как пути на диске D: (и аналогично для других букв дисков). (трекер: BUG-05.20 (BUG-098))

#### Scenario: Путь Git Bash

- **GIVEN** команда хода «cp data.bin /d/Portal/zai/shots/a.png»
- **WHEN** ответ показывается
- **THEN** превью картинки запрашивается по пути D:\Portal\zai\shots\a.png, а не под папкой чата

### Requirement: Итоговый файл хода при лимите списка

Серверный список файлов хода SHALL содержать не больше 40 файлов на окно. Если файлов больше, первыми SHALL идти документы и медиа в корне папки, затем документы и медиа в подпапках, затем остальное (скрипты, данные). Внутри группы поздние файлы SHALL идти раньше ранних. Ответ SHALL быть упорядочен по времени изменения. (трекер: BUG-181 / BUG-05.28)

#### Scenario: Много промежуточных файлов

- **GIVEN** за ход создано 84 файла (скрипты, картинки, превью), итоговый .pptx записан последним
- **WHEN** клиент запрашивает список файлов хода
- **THEN** .pptx в списке и получает карточку под ответом, где он назван

### Requirement: Параллельная загрузка одноимённых файлов
Сервер SHALL сохранять каждый загруженный файл под собственным именем, создавая файл эксклюзивно: одновременные загрузки с одинаковым именем не затирают друг друга.

#### Scenario: Двадцать загрузок одного имени
- **GIVEN** каталог загрузок чата
- **WHEN** одновременно приходят 20 загрузок файла `report.txt` с разным содержимым
- **THEN** в каталоге 20 файлов с разными именами, содержимое каждого совпадает с отправленным

### Requirement: Запрошенный файл виден в чате
Когда пользователь просит прислать или показать файл, а агент оформил его в ответе ссылкой с локальным абсолютным путём, чат SHALL показать карточку этого файла с просмотром и скачиванием прямо из места, где файл лежит, без копирования в папку чата — если файл доступен учётной записи пользователя. Путь, упомянутый в тексте без ссылки и лежащий вне папки чата, SHALL NOT становиться карточкой.

#### Scenario: Файл вне папки чата
- GIVEN файл лежит вне папки чата, в зоне, доступной учётной записи
- WHEN агент отвечает ссылкой на него
- THEN в ответе карточка файла с превью; в папке чата копии нет

#### Scenario: Файл недоступен
- GIVEN агент сослался на файл вне зон, доступных учётной записи, или на несуществующий файл
- WHEN ответ показан в чате
- THEN вместо карточки строка с именем файла и словами «Файл недоступен в этом чате»

#### Scenario: Упомянутый путь без ссылки
- GIVEN агент написал в тексте путь к файлу вне папки чата, не оформив ссылкой
- WHEN ответ показан в чате
- THEN карточки этого файла нет

### Requirement: Ответ без путей сервера
Текст ответа агента SHALL показываться без путей сервера для файлов, у которых есть карточка: ссылка на файл заменяется её названием, полный путь — именем файла, строка из одной ссылки убирается.

#### Scenario: Ссылка на файл в ответе
- GIVEN ответ содержит строку из одной ссылки на файл и карточка файла показана
- WHEN пользователь читает ответ
- THEN пути и повтора имени под карточкой нет

### Requirement: Число карточек файлов в сообщении
Сообщение SHALL показывать карточки всех файлов ответа числом до 40.

#### Scenario: Двенадцать файлов
- GIVEN агент показал двенадцать файлов в одном ответе
- WHEN ответ показан в чате
- THEN карточек двенадцать

### Requirement: Агенты знают правило показа файлов
Каждый ход обоих движков SHALL нести в системном промпте правило портала: пользователь работает только через чат; файл, который он просит, оформляется ссылкой с абсолютным путём, а не описывается путём. Правило SHALL идти отдельно от инструкций пользователя и не зависеть от их наличия.

#### Scenario: Пользователь без своих инструкций
- GIVEN у пользователя не заданы инструкции в настройках
- WHEN он отправляет сообщение
- THEN системный промпт хода содержит правило портала о файлах

### Requirement: Отмена хода не затирает свежие правки
Отмена хода SHALL непосредственно перед восстановлением каждого файла сверять его с состоянием, по которому рассчитан план отмены, и SHALL NOT затирать файл, изменённый после расчёта плана; такой файл попадает в список пропущенных.

#### Scenario: Правка во время отмены
- GIVEN ход изменил два файла, пользователь нажал «Отменить ход»
- WHEN один из файлов изменён человеком после расчёта плана, но до его применения
- THEN этот файл остаётся с правкой человека и показан как пропущенный; второй файл возвращён к состоянию до хода
